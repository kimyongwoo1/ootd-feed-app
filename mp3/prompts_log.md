# prompts_log — 미니 피드 앱 MP3 (상호작용과 안전장치)

- 사용한 AI 도구: Claude (Cowork)
- 기록 방식: **실제 입력**은 AI에게 보낸 문장을 그대로 옮겼다. 짧게 물어본 경우 그때 함께 보낸 자료와 원했던 내용을 **요청 의도**에 덧붙였다. **다시 쓴다면**은 결과를 보고 나서 이렇게 물었으면 더 빨랐겠다고 생각한 프롬프트다.
- '검증' 칸은 직접 실행해 보고 확인한 내용으로 채운다.

---

## 1. MP2 앱에 좋아요·댓글·신고 추가

- 실제 입력: "이제 mp3를 만들어야해 mp2를 베이스로 사진에 있는 기능들을 추가해야 해 구현 해줘" (MP3 가이드 화면 캡처 2장 첨부)
- 요청 의도: MP2 앱을 그대로 이어서, 가이드의 MVP("좋아요 토글과 댓글 작성이 두 기기 간 동기화되고, 신고하면 사유와 함께 서버에 기록")와 평가 기준 3개, 제출물 5개를 만족하게 만들고 싶었다.
- AI 응답: 서버에 좋아요·댓글·신고 테이블 3개를 추가하는 SQL, 앱의 좋아요 버튼·댓글 목록과 입력창·신고 시트, 그리고 README와 GUIDELINES.md를 작성. MP2 테이블이 있어도 그대로 실행되도록 SQL을 구성
- 판단: (초안) 채택. MP2에서 서버 코드를 `post_repository.dart` 한 곳에 모아 둔 덕분에, 화면은 함수 몇 개만 더 부르면 됐다.
- 다시 쓴다면: "첨부한 MP3 가이드의 평가 기준 3개에 맞춰서 MP2 앱에 좋아요(토글, 중복 방지), 댓글(목록·작성), 신고(사유 선택 → 서버 기록)를 추가해 줘. 중복 방지는 서버에서 막고, 기존 MP2 데이터는 지우지 않게."

## 2. 좋아요 — 토글과 중복 방지

- 실제 입력: (1번 요청에 포함) 가이드의 "게시글 좋아요(토글, 중복 방지)"
- AI 응답: 좋아요 테이블의 기본키를 (게시글, 사용자)로 정해 같은 사람이 두 번 저장할 수 없게 함. 좋아요 수는 앱이 계산하지 않고 서버 트리거가 자동으로 더하고 뺌. 앱은 누르는 즉시 화면을 바꾸고(낙관적 업데이트) 서버 결과로 다시 맞추며, 실패하면 원래대로 되돌림. 요청 중에는 버튼을 막아 연타로 인한 중복 요청 방지
- 판단: (초안) 채택. 중복 방지를 앱에서만 하면 두 기기에서 동시에 누르거나 요청이 두 번 갈 때 뚫릴 수 있어서, 서버에서 막는 방식이 맞다고 판단했다.
- 검증: (예: 같은 글에 ♥ 를 여러 번 눌러도 0 ↔ 1 만 반복되는 것 확인, 기기 B에서 새로고침 후 숫자 확인 → screenshots/)

## 3. 댓글 — 목록과 작성

- 실제 입력: (1번 요청에 포함) 가이드의 "댓글 작성·목록"
- AI 응답: 상세 화면 아래에 닉네임(선택)과 댓글 입력창을 두고, 목록은 오래된 순으로 표시. 댓글 수는 서버 트리거로 계산해 피드 카드에도 표시. 당겨서 새로고침하면 다른 기기의 댓글도 불러옴. 실패하면 입력한 댓글은 남기고 [다시 시도] 안내
- 판단: (초안) 채택. 상세에서 댓글을 달고 뒤로 가면 피드 카드의 댓글 수도 바로 바뀌도록 연결한 점이 좋았다.
- 검증: (예: 기기 A에서 댓글 → 기기 B에서 같은 글 새로고침 → 댓글 보임 → screenshots/)

## 4. 신고 — 사유 선택과 서버 기록

- 실제 입력: (1번 요청에 포함) 가이드의 "게시글 신고 기능(사유 선택 → 서버 기록)"
- AI 응답: 상세 화면 🚩 버튼 → 사유 5가지(스팸·광고, 욕설·혐오, 음란, 개인정보 노출, 기타) 중 하나를 골라야 [신고하기]가 켜짐. 서버는 정해진 5가지 값만 받고, 같은 글은 한 사람이 한 번만 신고 가능. 신고한 글은 내 피드에서 바로 숨기고, 서로 다른 3명이 신고하면 모두에게 임시로 숨김. 내 글에는 신고 버튼을 표시하지 않음
- 판단: (초안) 채택. 자동 숨김 기준을 1명으로 하면 한 사람이 마음에 안 드는 글을 지울 수 있어서 3명으로 정했다.
- 검증: (예: 신고 후 Supabase Table Editor → mini_reports 에 사유·설명·시각이 저장된 것 확인 → screenshots/)

## 5. 좋아요 노출 범위 정하기

- 실제 입력: (1번 요청에 포함) 가이드의 "상호작용 데이터(누가 좋아요했는지)의 노출 범위를 결정하고 이유를 기록"
- AI 응답: 좋아요는 숫자만 공개하고 누가 눌렀는지는 작성자에게도 공개하지 않는 방식을 제안. 화면에서 숨기는 것뿐 아니라 서버 규칙(RLS)으로 "내 좋아요만 읽기"를 걸어서, 앱을 고쳐 요청해도 다른 사람의 기록을 받을 수 없게 함. 신고자도 같은 방식으로 비공개
- 판단: (초안) 채택. 익명 SNS에서 좋아요 목록이 보이면 같은 사람의 활동을 모아 볼 수 있어 익명성이 깨진다고 생각했다. 작성자에게는 숫자만으로 충분하다.

## 6. 커뮤니티 가이드라인 작성

- 실제 입력: (1번 요청에 포함) 가이드의 "GUIDELINES.md — 금지 콘텐츠, 신고 처리 원칙, 상호작용 데이터 노출 범위와 이유"
- AI 응답: 금지 콘텐츠 5가지를 앱의 신고 사유와 1:1로 맞추고, 신고 처리를 접수 → 신고자 보호 → 자동 숨김 → 운영자 검토 → 결정의 5단계로 정리. 각 단계가 서버의 어느 규칙으로 지켜지는지 함께 적음
- 판단: (초안) 채택. 문서에 적은 규칙이 실제 서버 SQL과 일치하는지 하나씩 대조했다.
