## 1. BaaS 고르기 — Firebase vs Supabase

- 실제 입력: "이제 백엔드서비스 부분도 해야하는데 우리는 firebase랑 supabase를 비교해볼거야. 내가 보내준 파일을 토대로 크로스플랫폼 초안이랑 붙여서 작성해줄래?"
- 요청 의도: 팀 프로젝트에서 어떤 BaaS를 쓸지 정하기 위해 두 서비스를 비교한 보고서가 필요했다.
- AI 응답: 데이터 구조(문서 DB vs PostgreSQL), 접근 제어(Security Rules vs RLS), 익명 인증, 가격, Flutter 지원을 표로 비교. 게시글·댓글·좋아요처럼 관계가 있는 데이터는 Supabase가 유리하다고 정리
- 판단: 채택. 팀에서 Supabase로 정했고, MP2도 같은 서비스로 이어서 만들었다. README 1번의 비교 표는 이 내용을 MP2에 맞게 줄인 것이다.
- 다시 쓴다면: "게시글 피드 앱 기준으로 Firebase와 Supabase를 데이터 구조, 익명 인증, 보안 규칙, 무료 사용량으로 비교해 줘. 결론은 한 줄로."

## 2. Supabase 프로젝트 준비

- 실제 입력: "그럼 superbase 시작하는거 알려줘" → ".env에 암호가 있는데?" → (API 화면 캡처) "이거 카피해서 넣으면 된다는거지?"
- 요청 의도: Supabase 프로젝트를 만들고 앱에 연결하는 키를 어디서 복사하는지, `.env` 에 무엇을 넣어야 하는지 알고 싶었다.
- AI 응답: 프로젝트 생성 → 익명 로그인 켜기 → SQL 실행 → Project URL과 Publishable key 복사 순서를 안내. DB 비밀번호와 secret 키는 앱에 넣지 않는다고 설명. URL 뒤의 `/rest/v1/` 은 빼야 한다고 알려 줌
- 판단: 채택. 공개해도 되는 키(Publishable)와 넣으면 안 되는 키(secret, DB 비밀번호)를 구분할 수 있게 됐다.
- 검증: (직접 확인한 내용으로 고쳐 쓰기)

## 3. MP1 앱을 Supabase에 연결

- 실제 입력: "mp2도 이런식으로 만들어야 해 mp1에서 만든 내용을 가지고 Superbase에 연결해서 구현하는거 해줄래" (MP2 가이드 화면 캡처 2장 첨부)
- 요청 의도: MP1 앱 구조는 그대로 두고, 가이드의 MVP("기기 A에서 쓴 글이 서버에 저장되고 기기 B에서 새로고침하면 보이는 상태")와 평가 기준 3개, 제출물 5개를 만족하도록 바꾸고 싶었다.
- AI 응답: MP1의 화면 3개는 그대로 두고, 서버와 통신하는 코드를 `services/post_repository.dart` 한 곳에 모음. 화면은 이 파일만 사용하도록 바꾸고, 테스트에서는 가짜 서버로 바꿔 끼울 수 있게 함
- 판단: (초안) 채택. 화면 코드에 Supabase 코드가 섞이지 않아 MP1 코드와 비교하기 쉬웠다.
- 다시 쓴다면: "첨부한 MP2 가이드의 평가 기준 3개에 맞춰서 MP1 앱에 Supabase를 붙여 줘. 익명 인증만 쓰고, 화면 3개 구조는 유지하고, 서버 코드는 한 파일에 모아 줘."

## 4. 테이블과 접근 규칙(RLS)

- 실제 입력: (3번 요청에 포함) 가이드의 "익명 인증만 사용, 개인정보 수집 금지"
- AI 응답: `mini_posts` 테이블(id, author_id, nickname, content, created_at)을 SQL로 생성. 작성자 칸은 서버가 `auth.uid()` 로 자동 입력하고, RLS로 "로그인한 사용자만 읽기, 본인 ID로만 쓰기"를 설정. 1~200자 검사도 DB에 넣음. 이메일·전화번호 칸은 만들지 않음
- 판단: (초안) 채택. 앱에서 작성자 ID를 보내지 않으니 다른 사람 ID로 글을 쓰는 것을 서버가 막는다. 팀 프로젝트의 `posts` 테이블은 사진이 꼭 필요해서, MP2용 테이블을 따로 만들었다.
- 검증: (예: SQL 실행 후 Table Editor에서 mini_posts 테이블과 예시 글 3개 확인)

## 5. 익명 인증과 두 기기 동기화

- 실제 입력: (3번 요청에 포함) 가이드의 MVP "기기 A 작성 → 기기 B 새로고침"
- AI 응답: 앱 시작 시 세션이 없으면 `signInAnonymously()`. 피드 위에 익명 ID 앞 8자리를 보여 주고, 내가 쓴 글에는 `내 글` 표시. 피드는 당겨서 새로고침과 ↻ 버튼으로 다시 불러옴. Chrome에서는 마우스로 당길 수 있게 설정
- 판단: (초안) 채택. 익명 ID가 화면에 보여서 두 기기가 서로 다른 사용자라는 것을 스크린샷 한 장으로 보여 줄 수 있었다.
- 검증: (예: 기기 A와 B의 익명 ID가 다르고, A에서 쓴 글이 B에서 새로고침 후 보이는 것 확인 → screenshots/)

## 6. 설정 키 분리와 작성 실패 안내

- 실제 입력: (3번 요청에 포함) 가이드의 "설정 키가 분리되어 있고 작성 실패 안내가 처리되어 있다"
- AI 응답: URL과 키는 `.env` 에서 읽고 `.env.example` 만 제출. `.env` 가 없으면 안내 화면을 띄움. 서버 오류를 한국어 안내로 바꾸고, 게시 실패 시 입력한 글은 남겨 둔 채 [다시 시도] 버튼을 보여 줌. 10초 안에 응답이 없으면 시간 초과로 처리. 게시 중에는 버튼을 막아 중복 게시 방지
- 판단: (초안) 채택. 실패했을 때 쓴 글이 사라지지 않는 점이 사용자 입장에서 가장 중요하다고 생각했다.
- 검증: (예: Chrome F12 → Network → Offline 으로 바꾸고 게시 → 안내 문구 확인)
